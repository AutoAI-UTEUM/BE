# 백엔드 코딩 컨벤션

| 항목 | 내용 |
| --- | --- |
| 상태 | 초안 |
| 마지막 갱신 | 2026-07-10 |
| 적용 | Spring Backend |

## 1. 기본 원칙

- 도메인 규칙은 Controller가 아니라 Service/도메인 계층에 둡니다.
- 엔티티를 API 요청/응답으로 직접 사용하지 않습니다.
- 한 변경은 한 목적에 집중하며 관련 없는 리팩터링을 섞지 않습니다.
- 아직 필요하지 않은 추상화나 확장 포인트를 미리 만들지 않습니다.
- Spring과 FastAPI의 책임 경계를 넘는 편의 로직을 추가하지 않습니다.

## 2. 패키지 구조 초안

기능 중심 구조를 기본으로 검토합니다.

```text
io.edupilot
├─ global
│  ├─ config
│  ├─ error
│  ├─ response
│  └─ security
├─ auth
├─ user
├─ material
├─ session
├─ quiz
├─ diagnosis
├─ memory
└─ ai
```

각 도메인 내부의 `controller`, `service`, `repository`, `domain`, `dto` 세부 구조는 초기 세팅 시 확정합니다. 단순히 계층 수를 늘리기 위한 빈 추상화는 만들지 않습니다.

## 3. 이름과 API

- 클래스/enum: `PascalCase`, 메서드/변수: `camelCase`, 상수: `UPPER_SNAKE_CASE`
- DB: `snake_case`, JSON: `camelCase`
- Controller는 HTTP 변환과 검증, Service 호출만 담당합니다.
- 요청 DTO는 목적이 드러나는 이름을 사용합니다. 예: `CreateSessionRequest`.
- 응답 DTO는 정답/비밀 필드가 섞이지 않도록 공개 모델을 별도로 둡니다.
- API 경로의 명사는 복수형을 사용하고 동작은 HTTP 메서드로 표현합니다.

## 4. 트랜잭션

- 쓰기 유스케이스의 트랜잭션 경계를 Service에 둡니다.
- 조회는 필요한 경우 read-only 트랜잭션을 사용합니다.
- Grok/FastAPI 네트워크 호출 동안 DB 트랜잭션을 열어두지 않습니다.
- 외부 호출 전후 상태가 달라질 수 있으므로 버전/상태를 다시 검증합니다.
- 중복 턴/제출을 막을 멱등성 키와 유일 제약을 함께 고려합니다.

## 5. 예외와 응답

- 도메인 실패는 안정된 에러 코드가 있는 명시적 예외로 변환합니다.
- `@ControllerAdvice`에서 공통 응답으로 매핑합니다.
- 예외를 잡고 무시하거나 임의 기본값으로 성공 처리하지 않습니다.
- 내부 예외 메시지, SQL, stack trace를 클라이언트에 노출하지 않습니다.
- 오류 코드는 [에러 코드](error-code.md)와 함께 변경합니다.

## 6. JPA/DB

- 연관관계는 필요한 방향만 매핑하고 기본 fetch 전략을 의식적으로 선택합니다.
- API 직렬화로 지연 로딩을 유발하지 않습니다.
- 컬렉션 조회는 N+1 여부를 테스트/쿼리 로그로 확인합니다.
- JSON 컬럼은 스키마 버전을 보존하고, 빈번한 조회 필드는 별도 컬럼으로 둡니다.
- migration 없이 엔티티 자동 DDL로 운영 스키마를 변경하지 않습니다.

## 7. 보안

- 비밀번호, JWT, API Key, 운영 접속 정보를 로그/응답/문서 예시에 넣지 않습니다.
- 역할 검증과 리소스 소유권 검증을 별개로 수행합니다.
- 업로드 파일은 확장자만 믿지 않고 콘텐츠 타입/서명을 함께 검토합니다.
- 퀴즈 정답/루브릭 엔티티를 FE DTO에 매핑하지 않습니다.
- 내부 AI API도 네트워크 경계와 인증을 갖습니다.

## 8. AI 연동

- `AiClient`가 HTTP 세부사항과 DTO 매핑을 캡슐화합니다.
- 내부 요청/응답에는 `schemaVersion`, `turnId`, 추적 ID를 둡니다.
- timeout과 재시도는 명시적으로 설정하며 비멱등 호출을 무조건 재시도하지 않습니다.
- FastAPI의 `statePatch`, UI 액션, 채점 합계를 신뢰하지 않고 허용 목록/불변식을 검증합니다.
- mock/stub로 정상·timeout·오류·잘못된 스키마 계약 테스트를 작성합니다.

## 9. 테스트

- 테스트 이름은 조건과 기대 결과가 드러나게 작성합니다.
- 핵심 비즈니스 규칙, 권한, 상태 전이, 실패 복구를 우선합니다.
- 단순 getter/setter나 프레임워크 동작을 중복 검증하지 않습니다.
- Controller 테스트는 요청/응답/오류 계약을, Service 테스트는 규칙을 검증합니다.
- 시간·UUID·외부 AI 같은 비결정 요소는 주입 가능한 경계로 둡니다.

## 10. 로그

- 구조화 가능한 키로 `traceId`, `sessionId`, `turnId`, `errorCode`, 외부 호출 시간을 남깁니다.
- 전체 요청/응답 본문을 기본 로그로 남기지 않습니다.
- 환경별 로그 레벨을 분리하고 운영에서 debug 로그를 기본 활성화하지 않습니다.
- 사용자 입력과 AI 응답을 저장/로그할 때 개인정보·저작권·보관 정책을 먼저 확인합니다.
