# 보호자 팀 검토 구현 경계 (#526)

이 문서는 유료 본인확인 업체를 연결하지 않는 `TEAM_REVIEW`의 서버 구현을 설명한다. 최초 상태는 비활성이다. 신청서나 체크박스, 링크 방문, 메일 도착, 전화번호 소유 확인은 이용 승인으로 처리하지 않는다. 실제 수신함 연결과 발송은 이번 구현에 포함하지 않는다.

한국어 안내·회신·상태별 양식은 [양식 문서](guardian-team-review-forms.md), 요청과 응답은 [FE 계약](guardian-team-review-fe-contract.md)에 있다. 서버는 버전이 확정된 안내와 수신 창구가 모두 설정된 경우에만 양식을 생성한다. 신청번호로 대상을 표시하며 생년월일·아동 전체 프로필·주민등록번호·증빙 원본을 회신 양식에 요구하지 않는다.

## 활성화에 필요한 별도 결정

`edupilot.guardian.team.enabled=false`와 `policy-confirmed=false`가 기본이다. 활성화하려면 운영자가 다음 항목을 명시해야 한다. 누락·미승인 placeholder·제어문자 또는 부적합한 값이 있으면 애플리케이션 시작 단계에서 실패한다.

| 항목 | 구현 계약 |
| --- | --- |
| 안내 | 버전·SHA-256 digest·HTTPS 안내 URL, 실제 수집 항목·목적·보유 안내·거부 효과 |
| 회신 | 명시적 이메일 회신 또는 별도 승인된 전화 확인 창구; 확인수단은 설정된 창구와 일치해야 함 |
| 관계 확인 | 법정대리인 관계를 확인하는 운영 절차·담당자 체크리스트의 실제 기준 |
| 담당자 | 지정된 사용자 ID 목록과 현재 DB의 ACTIVE ADMIN 권한이 모두 필요 |
| 동의 범위 | 필수 SERVICE, 별도 안내가 확정된 경우에만 선택 EXTERNAL_AI |
| 기간 | 링크·신청 유효기간, 승인 증거 최대 보유기간과 승인 유효기간을 각각 명시; 증거 기한은 승인 유효기간보다 짧을 수 없음 |

승인 증거 보유기간·승인 유효기간·담당자 권한을 코드가 추론하거나 부여하지 않는다. 배포, 설정 활성화, 실제 정보 수집과 개별 승인은 별도 운영 작업이다. 법령에서 제시하는 이메일 경로는 동의 내용이 담긴 이메일과 명시적인 동의 회신을 전제로 한다. 이 구현만으로 법정대리인 관계가 확인되거나 적법성이 보장된다고 주장하지 않는다. [개인정보 보호법 시행령 제17조의2](https://law.go.kr/lsLinkCommonInfo.do?lspttninfSeq=182193).

## 상태·권한·동시 요청

사용자당 현재 신청은 하나이며 재신청은 같은 신청의 `generation`을 증가시킨다. `revision`과 idempotency key·입력 digest로 동시 승인/반려와 재시도를 처리한다. 재시도는 권한을 다시 확인하고, 같은 key에 다른 입력을 넣으면 충돌한다. 잠금 순서는 사용자 ID 순서의 사용자 행 다음 신청 행이다.

관리자 계정 정지·역할 변경은 요청자와 대상의 두 사용자 ID를 정렬하여 순서대로 쓰기 잠금한 뒤 이미 잠긴 행만 refresh한다. 현재 요청자가 ACTIVE ADMIN인지 같은 트랜잭션에서 다시 확인한다. 다른 ACTIVE ADMIN인 대상을 정지·강등하더라도 요청자가 커밋까지 ACTIVE ADMIN으로 남는다. 본인 정지·본인의 비ADMIN 변경은 기존 규칙대로 거부한다. 잠긴 행에서 얻은 활성 관리자 수의 하한으로 마지막 관리자 보호를 유지한다. 기존 `REQUIRED` 원자성과 격리 수준은 유지하며 보호자 검토와 AI 완료 경계도 같은 사용자 ID 순서를 사용한다.

현재 상태 재조회는 `UserCurrentStateRefresh`를 통해 이미 잠긴 User에만 수행한다. Hibernate 7.4.1은 같은 잠금 모드의 refresh에서 locking 절을 생략할 수 있으며, MySQL `REPEATABLE_READ`에서는 이 조회가 과거 스냅샷을 다시 읽는다. 공통 코드는 같은 managed 객체와 트랜잭션을 유지하고 ORM 잠금 기록만 잠시 조정하여 현재 PK locking read를 수행한다. DB 잠금은 해제하지 않으며, locking query의 flush로 생긴 높은 내부 WRITE 기록도 복구한다. 관리자 변경, AI 완료, 턴 저장, 사용자 변경 경계가 이 계약을 사용한다. Hibernate를 변경할 때는 실제 MySQL RR의 사전 READ/WRITE 잠금·동의 철회/재승인·미저장 프로필 보존 회귀를 다시 통과해야 한다. 잠긴 User가 Hibernate 프록시이면 현재 Session에 이미 로딩된 같은 User 구현 객체만 잠금 검사·refresh·모드 복구에 사용한다. 미로딩·분리·다른 Session의 프록시와 획득하지 않은 READ→WRITE 승격은 거부하며, 초기화·재연결·ID 기반 대체 조회를 수행하지 않는다. 실제 H2와 MySQL 프록시 회귀에서 동의 상태 갱신·객체 동일성·상위 잠금 모드·물리 DB 대기를 함께 검증한다.

웹 자기신고는 DECLARED로만 이동한다. 지정 담당자는 신청번호·버전·범위·명시적 회신·확인수단을 검토하여 근거 참조와 받은 시각만 등록한다. 회신 원문은 서버에 저장하지 않는다. 관계·연락처·근거·안내 범위 검토를 마친 승인만 REVIEW_PENDING에서 APPROVED로 이동한다. 반려·보완·철회·만료·탈퇴는 승인을 해제한다. 보완과 링크 재발급은 과거 확인·토큰을 무효화하며 첫 수집 기한을 연장하지 않는다.

토큰은 SHA-256 hash로 저장하며 HTTPS 링크 fragment와 POST JSON 본문으로만 전달한다. 토큰 만료·1회 사용·소유자 현재 상태를 서버에서 검사한다. 응답은 no-store/no-referrer를 적용한다. 공개 응답에는 담당자 전용 개인정보와 감사 이력을 포함하지 않는다.

## 이용·외부 AI·SSE 경계

NEW_SIGNUP의 이메일 증거, KST 출생연도 기준, LEGACY_EXEMPT 정책은 유지한다. 보호자가 필요한 계정은 활성화된 현재 정책과 같은 digest의 미만료 TEAM_APPROVED 승인이 있어야 업무 API를 이용한다. 필수 SERVICE 승인은 선택 EXTERNAL_AI 전송에 대한 동의를 대신하지 않는다.

승인·철회·재신청마다 `guardian_consent_epoch`가 증가한다. 외부 AI 호출 전에 현재 세대를 캡처하며 재시도·SSE 이벤트·최종 JSON·저장 시 같은 세대와 현재 동의 범위를 검사한다. AI를 기다리는 동안 사용자 행 잠금을 유지하지 않는다. 저장은 현재 사용자 행 읽기 잠금과 승인/철회 쓰기 잠금으로 직렬화한다. 철회 후 재승인하더라도 이전 요청의 늦은 응답은 저장하거나 반환하지 않는다. 이미 전송된 외부 요청을 되돌리는 기능은 아니다.

MCQ/OX의 결정적 채점에는 선택 AI 동의가 필요하지 않다. 오답 후속 AI 진단이 실행되면 해당 진단이 캡처한 사용자·동의 세대를 채점 서비스의 최종 JSON 검사까지 전달한다. 진단 저장 후 별도 트랜잭션에서 철회·재승인되면 새 승인이 유효해도 이전 세대의 응답은 차단한다. 철회 전에 유효한 동의로 이미 확정된 진단 기록은 이 응답 차단으로 삭제하지 않는다.

승인 당시 전체 안내·범위·보유·유효기간 설정 digest를 사용자 행에 기록한다. 현재 정책 변경·비활성·미준비 상태는 해당 보호자 승인 계정의 접근을 차단한다. 활성화나 정책 변경은 모든 인스턴스의 설정을 일치시켜야 한다.

## 개인정보 정리와 메일 경계

아동이 제공한 보호자 이름·연락처는 확인 목적에 한정한다. 첫 수집 시각과 미확인 파기 기한을 저장하고 거부·미확인 5일 조건을 적용한다. 재발급·연락처 정정·보완으로 시간을 새로 시작하지 않는다. 일반 PDF/렌더의 30일 보존은 보호자 연락처에 적용하지 않는다. 승인 시 연락처와 토큰은 제거하고, 확정된 승인 증거 보유기한에 근거 참조와 세대별 감사/멱등 이력을 정리한다.

승인 증거 설정은 최대 보유기한이다. 철회·반려·탈퇴 등에는 목적이 끝난 참조를 먼저 정리한다. 실제 법적 최소보존 의무 충족은 확정하지 않았으며 운영 검토가 필요하다. 정리 스케줄러는 기능이 꺼져 있어도 이미 저장된 기한만 사용한다. 서버 재시작 후 미완료 정리를 다시 조회하며 새 보유기간을 만들지 않는다. 프로세스 중단이나 정리 실패 중 기한 내 실제 파기를 보장하지 않으므로 활성화 전에 정리 작업과 실패·기한 모니터링을 확인해야 한다. 실제 외부 메일함·제공자·백업의 파기는 이 코드가 보장하지 않는다.

`GUARDIAN_TEAM_NOTICE`는 일반 EmailService/history/outbox 경로에서 수신자 이력 생성 전 차단한다. 기본 수동 양식 경로는 이 타입의 행을 생성하지 않는다. 향후 신뢰된 내부 경로가 연결한 메일에 대해서는 신청 트랜잭션 안에서 수신자·제목·제공자 참조·오류·암호화 본문·lease와 binding을 제거한다. 전역 발송 quota 수량·시각은 유지한다. 수신자 개인 quota 연결과 외부 발송 회수는 복원/보장하지 않는다.

## 마이그레이션과 rollback

| 버전 | 변경 |
| --- | --- |
| V61 | guardian_team_requests / guardian_team_events / guardian_team_operations; 사용자 unique, token hash, 세대·기한·상태 제약 |
| V62 | users의 승인 만료·선택 AI 동의·세대·정책 digest, TEAM_APPROVED 허용과 증거 제약 |
| V63 | guardian_team_mail_bindings FK, 메일 타입 CHECK 확장 |

기존 DOB·이메일 증거·cohort를 변경하거나 기존 사용자를 승인하는 backfill은 없다. 배포 시 기존 V1~V60 이후 순서대로 적용해야 한다. 합성 로컬 MySQL에서 전체 순서와 기존 데이터 보존을 검증하며 운영 migration은 실행하지 않는다.

비활성화는 기존 승인 접근도 차단하지만 데이터를 이전 enum으로 바꾸지는 않는다. TEAM_APPROVED 또는 GUARDIAN_TEAM_NOTICE가 존재하면 이를 읽지 못하는 이전 binary로 직접 downgrade하지 않는다. 호환 reader를 유지하거나 forward fix한다. 스키마 DROP을 rollback 절차로 제공하지 않는다.

## 검증 범위

단위·H2/JPA·API 테스트는 합성 계정과 가짜 AI만 사용한다. 기본 비활성/불완전 설정, 현재 담당자 권한 회수, 토큰·공지 불일치·반복 요청, 동시 승인/반려, 5일 기한·재발급, 철회/재승인과 늦은 AI/SSE, 업무와 선택 AI 동의 분리, 탈퇴 rollback 및 메일 목적별 정리를 검증한다. 선택 MySQL 테스트는 전용 127.0.0.1:33316 합성 스키마에서만 실행하도록 제한한다.

관리자/User 잠금 회귀는 실제 MySQL 인덱스와 서비스 트랜잭션을 사용하여 ACTIVE/SUSPENDED 신청자, 정지/역할 변경, 대기 중 요청자 권한 회수와 기존 영속성 문맥을 구분한다. MCQ/OX 후속 진단 회귀는 진단 저장 이후 별도 커밋으로 동의를 철회·재승인하여 최종 응답 차단과 기존 유효 기록 보존을 함께 확인한다.

실제 아동 정보, 운영 DB, 실제 수신·발송, 개별 승인, 외부 업체·실학생 데이터·유료 AI와 백업 복구는 이 검증에 포함하지 않는다. 실행 결과와 조건부 미실행은 PR에 구분해서 기록한다. 현재 develop 자동 배포 보류를 유지하며 기능 브랜치와 draft PR로 제공한다.
