# DEV V66 릴리스 준비

**서버 실행 경로 아님.** 운영 서버, `main` 브랜치, 기존 V64/V65 런타임 가드는 이 절차의 범위 밖이다. `V66__learning_quiz_drafts.sql`은 학습 퀴즈 임시저장 컬럼을 추가한다. 자료 진행률·임시저장 API는 Spring에 있고 난이도 생성은 Spring과 AI를 함께 필요로 한다.

## 1. 출판 전 검증

- `python3 -I -S -B scripts/deploy/dev_v66_source_preflight.py`: 기존 V1–V65 Flyway 서명과 새 V66을 고정값으로 검사한다. 서버를 조회하지 않으며 배포 근거로 대체할 수 없다.
- 기존 V64/V65 검증기가 V66을 계속 거절하는지 확인한다. 거부를 우회하지 않는다.
- 별도 작업 브랜치에서 `develop` 대상 PR로 Main/AI CI 및 Isolated Guardian MySQL 검증을 실행한다. 격리 테스트에서 Flyway로 V65를 적용한 뒤 퀴즈를 추가하고, V66 한 건만 적용하며 기존 퀴즈 보존과 임시저장 버전 검사까지 확인한다.
- `Build DEV V66 images`는 검토된 `develop` SHA에서 수동 실행할 때만 Spring과 AI 이미지를 출판한다. 해당 SHA의 Main/AI CI, 동일 트리의 성공한 격리 MySQL PR 실행이 필요하다. 서버에 접속하지 않으며 DEV 전용 태그를 쓰고 결과는 digest 두 개로 식별한다. 이미지 하나만 성공하면 릴리스 후보가 아니다.

## 2. 실제 DEV 적용 전 차단 조건

- 신뢰된 호스트키와 실제 DEV 호스트의 연결, 현재 실행 중인 각 컨테이너와 검토된 이전 digest, Compose/Nginx 설정 및 DB Flyway baseline을 다시 확인한다. V65 baseline과 서명이 맞지 않으면 V66과 묶어 적용하지 않는다.
- 실제 쓰기 종료 후 최신 DB·파일·삭제 원장 복구 지점을 만들고 별도 환경에서 복원 가능성을 확인한다. 쓰기 중단·서비스 교체 예산·AI 작업 종료·자원 여유는 실제 결과가 필요하다. 출판 결과만으로 작업 창을 열지 않는다.
- 승인 및 검토된 V66 런타임 경로가 필요하다. 기존 V65 workflow에 V66 입력을 넣거나 Flyway 검증을 비활성화하지 않는다. 공유 `TAG`를 바꾸어 전체 서비스를 올리지 않는다.

## 3. 적용 및 검증 순서

1. 승인된 DEV 경로에서 AI만 먼저 고정 digest로 교체한다. 기존 난이도 없는 요청의 호환성을 확인한다. MySQL/Nginx와 Spring의 교체를 함께 요청하지 않는다.
2. AI 교체 뒤 새 baseline과 2절 증거를 검토하고, 별도의 V66 런타임 절차로 Spring만 교체한다. flyway_schema_history에 V66 성공·실패 0건, 기존 퀴즈 보존, Spring/AI health를 확인한다.
3. DEV 시험 데이터로 자료 진행률, 퀴즈 임시저장 GET/PUT/버전 충돌/제출 시 정리, 난이도 생략 호환성을 확인한다. 외부 AI 비용이 드는 난이도 생성과 FE 연동은 따로 확인한다. 기존 FE가 API를 연결하기 전에는 화면에서 세 기능이 작동한다고 보고하지 않는다.
4. V66 적용 뒤 장애 시 자동으로 과거 Spring 이미지를 시작하거나 DDL을 되돌리지 않는다. 안전하게 접근을 유지·차단할지 판단한 뒤 호환되는 수정본 또는 검증된 별도 복구 절차를 검토한다.
